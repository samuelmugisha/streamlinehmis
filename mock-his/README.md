# mock-his — demo-only stub upstream

**Not part of Hospilot.** The real product's README is explicit: the hospital
HIS/EHR that Fabric talks to is "the real hospital system — never provisioned
by this repo." Without one, every Fabric-backed query (admissions, locations,
anything that isn't the hand-seeded Redis bed cache) hard-fails with a 500,
which in turn trips the planner's execution-failure re-orchestration loop for
any goal that touches staffing, ICU, ER, or discharge.

This is a minimal stand-in FHIR R5 server, stdlib-only (no dependencies to
install), that serves exactly two resource types with real sample data —
`Location` (20 beds) and `Encounter` (9 inpatient admissions) — generated by
`fhirgw.mappers.location.to_fhir` / `fhirgw.mappers.encounter.admission_to_fhir`
(Fabric's own mappers, run once inside the fabric container and dumped to
`fixtures.json`), so the shape is guaranteed to round-trip through Fabric's
real `to_internal()` parsing. Bed ids/wards/status mirror
`agentic-framework/scripts/seed_redis.py` exactly.

Every other FHIR resource type (`Patient`, `Observation`, `Task`,
`ServiceRequest`, `Composition`, `Specimen`, `Device`, `MedicationRequest`,
`Organization`, ...) returns an empty search Bundle rather than erroring —
those agents (lab, pharmacy, patient verification, ...) get "no data" instead
of a 500, which is a better failure mode for a demo even though it isn't a
real fix. Writes (`PATCH`/`PUT`) are accepted and echoed back but not
persisted — this is a read-only fixture server.

To regenerate `fixtures.json` after changing the bed/admission list, edit
the generator and re-run it inside a running fabric container (needs
`fhir.resources` + `fhirgw`, both only available there):
```bash
docker cp gen_fixtures.py <fabric-container>:/tmp/gen.py
docker exec <fabric-container> python3 /tmp/gen.py > mock-his/fixtures.json
```

Wire it up by pointing `fabric/.env`'s `EHR_FHIR_BASE_URL` at
`http://mock-his:9000/fhir` (the compose service name) and recreating the
fabric container — `docker restart` is not enough, `env_file` values are only
read at container creation (`docker compose ... up -d --force-recreate fabric`).

## Generated demo data (`demo_data.py`)

Beyond the bed/admission fixtures above, `demo_data.py` generates the Carer Demo
Hospital's operational data — invoices, claims, payments, contracts, appointments,
doctor slots, waitlist, lab orders/results/samples/analyzers/rules, pharmacy
orders/inventory/logs/rules, staff roster + staff, and OT rooms/schedule/surgeries/
equipment. Ids are deterministic and every date is relative to today, so it never
goes stale. `app.py` builds it at startup and serves it on `/api/<financial|appointments|
pharmacy|lab|ot>/...`, `/api/sync/<table>` and FHIR (`Patient`, `ServiceRequest`,
lab `Observation`, `Specimen`, `Device`).

Some agents also read the Hasura mirror directly, so load the same rows into Postgres
(idempotent — re-run to refresh the dates), then restart the backend to re-sync:
```bash
python3 mock-his/demo_data.py --sql | docker exec -i hospilot-oss-hasura-postgres-1 psql -q -U hospilot -d hospilot
docker restart hospilot-oss-mock-his-1 hospilot-oss-backend-1
```
The Hugging Face image does both on every boot (`deployments/huggingface/start.sh`).
